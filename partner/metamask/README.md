# MetaMask delegation settlement

A verdict-gated ERC-7710 delegation built with the MetaMask Smart Accounts Kit. The principal's MetaMask smart account delegates "pay the agent exactly the fee, once, before expiry" to a settlement account (the clerk). The clerk redeems only after the GenLayer MandateVerdict contract returns TRUE. See [MetaMask delegation settlement](../../README.md#metamask-delegation-settlement) in the main README for the design.

**Trust model, briefly:**
- **On-chain verdict check (third run).** `VerdictGateEnforcer` (`contracts/`) is a custom caveat: MetaMask's DelegationManager refuses the redemption until the carrier named in the signed delegation has recorded TRUE for exactly this case on Sepolia. That moves the verdict gate and the case label on-chain, and the agent redeems for itself. **The carrier is still trusted:** it is a trusted off-chain writer (no contract on Sepolia checks GenLayer itself), trusted to post only a finalized TRUE. It cannot change the amount, the recipient or any other limit, or post for a delegation that names another carrier. A posted TRUE cannot be undone. After it, the principal's only remedies are to disable the delegation (`disableDelegation`) or let it expire. One post opens every delegation that names that carrier and that case: the once-only limit (`limitedCalls`) is per delegation, not per case. See [On-chain verdict check on Sepolia](#on-chain-verdict-check-on-sepolia).
- **The clerk is trusted (payment and refusal runs).** The verdict gate and the case label (the salt) are checked only by the clerk's code in `settle()`, not on-chain; nothing on Sepolia checks GenLayer Bradbury. A dishonest clerk could pay the agent on a FALSE verdict or for the wrong case. MetaMask's caveat enforcers still stop it from paying anyone else, paying more, paying twice, or paying after expiry.
- **It isn't an escrow.** The fee stays in the principal's own smart account, and the owner could move it out before redemption.
- **The expiry is up to the caller.** The live runner defaults to 7 days (`EXPIRY_DAYS`); `buildPaymentDelegation` accepts any expiry. `settle()` reads the expiry from the signed delegation's Timestamp caveat.

### Refusal on Sepolia

On 16 November 2026 (22:52–22:53 UTC) `node scripts/refusal.mjs run --broadcast` ran on public Sepolia with the same throwaway accounts. The clerk's `settle()` refused, with no transaction, a fresh delegation bound to another case, even though the sample case's live verdict was TRUE. Then two redemptions were sent with a fixed gas limit so they would be mined, and both reverted:

|---|---|---|---|
| R1. The agent redeems the fresh delegation itself | [`0x323887a0…`](https://sepolia.etherscan.io/tx/0x323887a077ab6f8be8226ab47f259f7a1b6562df2627db31f8ee5e592c33528b) | 12150397 | reverted: DelegationManager `InvalidDelegate` |
| R2. The clerk redeems the delegation paid in step C again | [`0x28c9837c…`](https://sepolia.etherscan.io/tx/0x28c9837c4137efd47ef85cac8940499cb792dfbc53b8860d9a41b3f92755d640) | 12150399 | reverted: `NativeTokenTransferAmountEnforcer:allowance-exceeded` |

The agent's throwaway key sent and paid for R1 (2,532,840 wei of gas), so a rerun needs a little Sepolia ETH on the agent address; the clerk paid for R2. The principal's smart account held 0 ETH during R1, so R1 shows the delegate (caller) check, not a funded payment being blocked.

The runner now sends R1 or R2 only if an `eth_call` simulation reverts with the expected decoded reason (any RPC error, rate limit or other reason aborts before sending), requires a `reverted` receipt and a matching parent-block replay after mining, exits non-zero and writes nothing otherwise, and never overwrites an existing record (`run --broadcast --out <new-file>`). `node scripts/refusal.mjs verify` re-checks the recorded R1 and R2 read-only (it needs an archive-capable Sepolia RPC in `SEPOLIA_RPC_URL`); its 16 November 2026 result is under `independentReverification`. The gate is unit-tested in [`test/refusal-gate.test.mjs`](test/refusal-gate.test.mjs).

Record: [`live-refusal-result.json`](live-refusal-result.json). Still not run on a public chain: a live FALSE or UNDETERMINED verdict (the only deployed case resolved TRUE, and no new GenLayer transactions were made) and a redemption after expiry. Those are covered by the unit tests and the local fork simulation.

The runner uses the same evidence gate as the refusal run. Each step was sent only if its `eth_call` simulation showed the expected outcome. For T3, the call also had to succeed once `verdictTrue` was overridden to TRUE (an `eth_call` state override). That is a simulation pinned at T2's block (12150801), not a trace of the mined T3: in that simulation, the gate was the only obstacle. The block is recorded under `counterfactual`. After mining it checks the receipts, a parent-block replay of T3, the event and storage, and the exact balance changes. It caps itself at five transactions, and it never overwrites a record.

The first attempt aborted after T2 on a stale balance read from a load-balanced RPC node (T2 had succeeded). The `--resume` mode re-verified T1 and T2 on-chain, kept them in the same five-transaction budget, reused the signed delegation, and pinned later reads to explicit blocks; see `resumedFrom` in the record. Nonces (read-only, re-checked by `verify`): between the block before T1 and T5's block the clerk's nonce went 4 → 7 and the agent's 1 → 3, so exactly five transactions from these accounts were mined in that interval, the five in the record. The agent's nonce was still 1 at block 12150816, after T2, so no agent transaction was mined before the recorded T3. Nonces show only what was mined, not what was broadcast. That no T3 was broadcast before the abort rests on the run log and the code order: the first run threw at the T2 balance check, which comes before the T3 simulation and send, and its console log ([`live-onchain-check-run1.console.log`](live-onchain-check-run1.console.log), committed verbatim) shows T1 and T2 sent and no T3. The whole flow, and then the resume path, were rehearsed on a local anvil fork first. Full write-up: [On-chain verdict check on Sepolia](../../README.md#on-chain-verdict-check-on-sepolia).

**Resume safety (since the run).** `scripts/onchain-check.mjs` now journals each send to `<out>.journal.jsonl` (the nonce before the send, the hash as soon as it returns, both fsync'd) and resumes only when the journal and the chain's nonces and receipts agree that exactly T1 and T2 were sent and nothing is pending; T2 comes from the journal, and `--t2-hash` is gone. A missing hash, an already-sent T3 or an unexplained nonce is refused. An incomplete record is single-use by content and by run, not by path: before the resumed run can send, the runner exclusively creates `run-<runId>` and `content-<sha256>` markers in a fixed per-machine ledger (`~/.onchain-check/consumed-resumes`), so a copy, rename, edited record file or deleted `<record>.consumed` marker is refused (editing the journal's start entry changes the run id, so a deliberate edit of both the record and the journal escapes the ledger). **Operators: do not copy, rename or edit an incomplete record, or delete its markers or the ledger, to resume it again.** This is cooperative, local-scope protection, not tamper resistance: the ledger is per machine and per ledger directory, and another machine, user, or `ONCHAIN_CHECK_LEDGER_DIR` pointed at an empty directory bypasses it (that variable exists for tests). The pinned-nonce check still refuses any resume whose nonces don't match the journal. A send error that carries a transaction hash has that hash journaled before the error is rethrown. See `src/send-journal.mjs` and `test/send-journal.test.mjs`.
