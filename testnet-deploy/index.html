Partner settlement: MetaMask delegation

The verdict above also decides a payment. Using the MetaMask Smart Accounts Kit (an ERC-7710 delegation), the principal's MetaMask smart account on Ethereum Sepolia lets a settlement account, the clerk, pay the agent, but only in one exact way.

Live on Sepolia: verdict TRUE → agent paid 0.001 ETH Live on Sepolia: an outsider's redemption and a repeat redemption both reverted Live on Sepolia: on-chain verdict check, blocked before the verdict was posted, paid after

  1. 1 · GrantThe principal signs one delegation to the clerk: “pay the agent exactly 0.001 ETH, once, before expiry.” This is an off-chain signature, not a transaction.
  2. 2 · Verdict TRUE → paidThe clerk reads get_verdict from this GenLayer contract. On a resolved TRUE it redeems the delegation through MetaMask's DelegationManager, and the agent receives 0.001 ETH.
  3. 3 · FALSE or UNDETERMINED → refusedThe clerk does not redeem, and the delegation lapses at its expiry. An unresolved case waits.

On-chain verdict check: what moved on-chain, and who is still trusted

In the payment run (A–C), the verdict gate and the case label were checked only by the clerk's code. In the on-chain check (T1–T5), they are a caveat on the delegation itself. MetaMask's DelegationManager calls VerdictGateEnforcer on every redemption, and it reverts unless the carrier named in the signed delegation has recorded TRUE for exactly this case. The agent redeems for itself, and no clerk code sits between the recorded verdict and the payment.

Not trustless. Ethereum Sepolia cannot read GenLayer. The carrier (here the clerk's throwaway key) is trusted to post TRUE only after reading a finalized TRUE verdict from this contract, and no contract on Sepolia checks that it told the truth. It is a trusted relayer, not an oracle. What the carrier cannot do: change the amount, the recipient or any other limit, post for a delegation that names a different carrier, or undo a post. Anyone can compare its post with get_verdict above.

Limits checked on-chain by MetaMask's Delegation Framework

  • Spending cap: at most the 0.001 ETH fee, in total (nativeTokenTransferAmount)
  • Plain transfer: requires empty calldata; no function call (exactCalldata with empty terms, added by the spending-cap scope)
  • Exact payment: the only allowed call sends exactly the fee to the named agent (exactExecution)
  • Clerk only (runs A–C and R1–R2): no other account can redeem (the delegation names the clerk as its delegate, and the redeemer caveat repeats it). In the on-chain check (T1–T5), the delegate and only redeemer is the agent itself
  • Verdict recorded (on-chain check only): redeemable only after the named carrier has recorded TRUE for this case in VerdictGateEnforcer (a custom caveat: 71 lines of Solidity, no owner or admin, source verified)
  • Once: a single redemption (limitedCalls)
  • Expiry: only before a deadline (timestamp; the payment run used 7 days, the refusal run's fresh delegation one hour)

What this does not prove

  • The clerk is trusted in A–C; the carrier is trusted in T1–T5. GenLayer and Sepolia have no oracle between them. In the payment run, only the clerk's code checks the verdict and the case label (a salt derived from GenLayer chain 4221 + this contract). In the on-chain check, a Sepolia contract checks that the named carrier posted TRUE for this case, but whether the GenLayer verdict really is TRUE still rests on the carrier.
  • It isn't an escrow. The fee sits in the principal's own smart account, and the owner could move it out before redemption.
  • One operator. The same operator held the throwaway owner, clerk and agent keys. The clerk paid the gas and funded the fee for the payment run; in the refusal run the agent paid R1's gas from the fee it had received. In the on-chain check the clerk paid for T1, T2 and T4, and the agent paid for T3 and T5. So the carrier and the agent being different people is not shown, only that the chain enforces the rule between them.
  • Now live on Sepolia, not just simulated: an outsider redemption and a second redemption, both reverted on-chain (R1, R2). R1 was stopped by the DelegationManager's delegate check before the redeemer caveat ran; the principal's smart account held 0 ETH at the time, so R1 shows that caller check, not a funded payment being blocked. R2 was stopped by the spending cap; the limitedCalls count was already 1 and would also have blocked it.
  • Still simulated only: a live FALSE or UNDETERMINED verdict (the only deployed case resolved TRUE, and no new GenLayer transactions were made), and a redemption after expiry. Those run in the unit tests and on a local Sepolia fork. The refusal in the first refusal row is the clerk's code, not a chain rule. The gate has no way to post FALSE: on Sepolia, a FALSE case looks the same as one that was never posted, and T3 shows that state blocking a funded payment.
